================================================================================
1. ¿QUÉ ES ESTE PROYECTO?
================================================================================

`ggtucdf` es el sitio web oficial del artista musical "Gargut" (nombre artístico
completo: "Garguttieneunchingodeferia"), un artista de música urbana, trap y rap
mexicano originario de Guadalajara, México.

El sitio funciona como:
  - Portafolio y carta de presentación del artista.
  - Hub de fans ("Fan Hub") donde los seguidores se registran para recibir
    contenido exclusivo y el enlace al canal de difusión de WhatsApp.
  - Escaparate de la discografía completa (11 lanzamientos entre 2025 y 2026).
  - Centro de videos (YouTube, Instagram Reels, TikTok).
  - Sistema de "drops" (lanzamientos) con contador regresivo configurable.
  - Punto de entrada para el reproductor dinámico de Spotify que siempre muestra
    el último lanzamiento del artista.
  - Herramienta de administración para que el artista (o su equipo) gestione la
    lista de fans registrados y pueda copiar sus números de WhatsApp para el
    canal de difusión.

El proyecto fue construido por WildForgeLabs (estudio de desarrollo) para el
artista. La marca WildForgeLabs aparece discretamente en el footer de todas las
páginas como crédito de desarrollo.

Dominio de producción: https://garguttieneunchingodeferia.com
Repositorio: https://github.com/redkazta/ggtucdf
Proyecto Supabase: https://coilzxaisyuvcsdbywrk.supabase.co (región us-east-2)

2. STACK TECNOLÓGICO COMPLETO
================================================================================

FRONTEND:
  - Astro 6.1.5+ (framework principal, output: "hybrid" para permitir API
    routes server-side).
  - TypeScript (tipado en todo el proyecto).
  - CSS puro (sin Tailwind instalado actualmente, aunque el prompt maestro
    original lo mencionaba; el diseño se hace con CSS scoped de Astro).
  - Fuentes: "Archivo Black" (para el hero del index), "Bebas Neue" (para
    títulos, navegación y botones), "Inter" (para texto general). Cargadas
    desde Google Fonts.
  - JavaScript vanilla para interactividad (scripts inline y client:load).

BACKEND / SERVICIOS:
  - Supabase (PostgreSQL) para la base de datos de fans.
  - Resend para el envío de emails automáticos de bienvenida.
  - Spotify Web API (Client Credentials flow) para obtener el último
    lanzamiento del artista.
  - Vercel como plataforma de deploy (adapter @astrojs/vercel).
  - @vercel/analytics para métricas de tráfico.

INFRAESTRUCTURA:
  - GitHub (repo: redkazta/ggtucdf).
  - Vercel (deploy automático desde main).
  - Supabase (base de datos + storage del video del hero).

  - Título "Música".

  - Layout: ArtistLayout.
  - Sección 01 / Destacados:

    - 4 reels sin título.
  - Grids responsive: 1 col mobile, 2 col tablet, 3-4 col desktop.
  - PageFooter.

▶ /admin (admin.astro)
  - Página protegida con contraseña simple (PRIVATE_ADMIN_TOKEN en .env, por
    defecto "gargut123").
  - Login: input de contraseña + botón "Entrar".
  - Al autenticarse, muestra AdminTable.
  - AdminTable:
    - Fetch a /api/fans.
    - Tabla responsive: Nombre, Email, WhatsApp, Fecha, Acción.
    - Botón "Copiar" por fila (copia el WhatsApp al portapapeles).
    - Botón "Copiar todos los números (coma-separados)".
    - Toasts de confirmación.
    - Estados: loading, error, empty.
  - NOTA: Usa autenticación simple por contraseña, no Supabase Auth (MVP).

▶ /api/register-fan (POST)
  - Recibe JSON: { nombre, email, whatsapp, acepto_privacidad }.
  - Valida en frontend antes de enviar (email regex, WhatsApp regex, checkbox).
  - Inserta en tabla `fans_gargut` de Supabase (service_role key).
  - Envía email de bienvenida vía Resend con enlace al canal de WhatsApp.
  - Retorna { success: true } o error 500.

▶ /api/fans (GET)
  - Lista todos los fans de `fans_gargut` ordenados por created_at DESC.
  - Retorna { fans: [...] }.
  - Usado por el AdminTable.

▶ /api/latest-spotify (GET)
  - Obtiene token de Spotify (Client Credentials flow).
  - Consulta GET /v1/artists/{id}/albums?include_groups=album,single&limit=1&sort=release_date_desc.
  - Retorna { id: "trackId" } del último lanzamiento.
  - Si falla, el frontend usa fallback (SPOTIFY_TRACK_ID estático).
  - Las 3 API routes tienen `export const prerender = false` para que no se
    prerendericen en build time (evita errores de credenciales).

12. FLUJO TÉCNICO DEL REPRODUCTOR DINÁMICO DE SPOTIFY
================================================================================

  1. El usuario carga /musica.
  2. SpotifyLatestPlayer.astro (client:load) hace fetch a /api/latest-spotify.
  3. /api/latest-spotify:
     a. Pide token a https://accounts.spotify.com/api/token con
        grant_type=client_credentials, client_id y client_secret.
     b. Con el token, consulta:
        GET https://api.spotify.com/v1/artists/{SPOTIFY_ARTIST_ID}/albums
            ?include_groups=album,single&limit=1&sort=release_date_desc
     c. Extrae el ID del track (items[0].tracks[0].id o items[0].id).
     d. Retorna { id }.
  4. El componente genera dinámicamente:
     <iframe src="https://open.spotify.com/embed/track/{id}">
  5. Si algo falla, usa SPOTIFY_TRACK_ID (4KvIxXUbDzMicaBr2opF9e) como
     fallback.

  IMPORTANTE: Spotify no tiene webhooks para nuevos lanzamientos. La única
  forma de mantenerlo actualizado es consultar la API (como se hace aquí) o
  usar un cron job. Este diseño consulta en cada carga de página.

13. SEGURIDAD Y CONSIDERACIONES
================================================================================

  - La service_role key de Supabase y la API key de Resend NUNCA se exponen al
    cliente (solo en API routes server-side).
  - El admin actual usa una contraseña simple (PRIVATE_ADMIN_TOKEN). Para
    producción real se recomienda Supabase Auth.
  - La API /api/fans no tiene autenticación server-side (cualquiera que conozca
    la URL puede listar los fans). Se recomienda añadir un token o auth.
  - La tabla fans_gargut no tiene RLS habilitado por defecto (comentado en el
    SQL). Se recomienda habilitarlo y crear políticas adecuadas.
  - El formulario valida email y WhatsApp en el cliente, pero el backend no
    re-valida (se podría añadir validación con Zod o similar).
  - Los headers de seguridad en vercel.json mitigan clickjacking, MIME sniffing
    y filtrado de referrer.
  - El correo de Resend usa un enlace placeholder a WhatsApp
    (https://chat.whatsapp.com/XXXXX) que debe reemplazarse por el real.
